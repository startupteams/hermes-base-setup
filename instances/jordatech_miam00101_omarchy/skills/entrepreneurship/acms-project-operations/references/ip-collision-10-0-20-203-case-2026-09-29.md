# IP-collision on 10.0.20.203 — full case file (2026-09-29)

The template-clone IP collision that briefly broke ACMS→worker dispatch.
Full detail preserved here; the durable checklist lives in
`llm-manager-operations/references/opnsense-access-and-ip-vetting.md`.

## Symptoms (why it was sneaky)

- ACMS on CT122 got **connection refused** on `10.0.20.203:8402` while the
  worker (VM124) provably listened on `0.0.0.0:8402`, had no firewall, was
  pingable, and the subnet was right. Every app-level check passed.
- ARP on CT122 resolved `10.0.20.203` → MAC `bc:24:11:2f:f4:5f`, but VM124's
  NIC MAC was `BC:24:11:C3:C1:AD`. **Another guest was answering .203.**
  Inbound bridge traffic was landing on the impostor (its sshd answered :22;
  nothing answered :8402).

## Root cause

VM108 (`stea-biraj-persistent`) was cloned from a shared template that carried
a **static netplan entry for 10.0.20.203**. Template-clone hygiene (re-identify
IP / machine-id / host keys) was skipped, and the impostor won whenever it
booted most recently (ARP favored the newest advertisement).

## Fix

VM108 renumbered to `.204` after vetting it free against OPNsense (Kea
reservations + legacy static maps), live ARP from ≥2 vantage points, and PVE
guest config. No PVE config change needed for VM124 — the worker was right;
the squatter moved.

## Generalization

- Any guest cloned from a VM/template with netplan-static networking carries
  the donor's IP. **Template-clone hygiene MUST re-identify: netplan IP,
  machine-id, SSH host keys.**
- Dispatch/routing targets pinned by IP (e.g. `ACMS_BRIDGE_TARGETS_JSON`) are
  only as trustworthy as the ARP table; prefer DNS indirection (logged as
  FUTURE_WORK in the ACMS repo).
- Diagnose at the ARP/MAC layer BEFORE changing any config: `ip neigh` on the
  caller, compare against the guest's actual NIC MAC from PVE config.
