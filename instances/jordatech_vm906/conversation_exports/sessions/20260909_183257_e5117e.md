## 1. Executive objective

Create a dedicated VM named:

```text
MARION-IA-USA LLM Manager
```

on `MIAM-00135`, initially bootstrapped from the known-good GPU Driver Installer controller VM architecture but fully re-identified and stripped of copied GDI secrets/state.

The LLM Manager will become the stable point through which local Hermes agents and other authorized internal clients use LLM inference. It should:

- monitor and control vLLM deployments on `MIAM-00111`, `MIAM-00112`, `MIAM-00143`, and `MIAM-00144`
- issue a distinct API key to each Hermes agent
- expose a stable OpenAI-compatible endpoint
- route requests to healthy local deployments first
- wait a deliberate, configurable interval for local capacity instead of prematurely buying cloud inference
- fall back to OpenRouter only when policy permits and local capacity/health criteria are not satisfied
- enforce OpenRouter spend caps and per-agent policy
- benchmark model/topology combinations and keep historical results
- collect GPU, vLLM, request, health, and power telemetry
- calculate energy cost and performance-per-dollar
- use GPU onboard telemetry as the primary dynamic local power signal
- ingest Emporia whole-circuit/PDU/mini-split data as an independent facility-level measurement source
- store operational metadata and history in PostgreSQL
- offload high-volume or full prompt/response history away from the constrained `MIAM-00135` system disk
- provide controlled vLLM service lifecycle actions and bounded VM recovery actions
- provide a future path for multi-node vLLM deployments using the 100 Gb interconnect between `MIAM-00111`, `MIAM-00143`, and `MIAM-00144`
- eventually compare/rank local inference, OpenRouter, direct APIs, and other officially supported provider integrations by availability, quality, cost, performance, context, privacy, and policy

The LLM Manager is a **control plane and gateway**. It does not normally host model weights or perform GPU inference itself.

The number of issued API keys should **not** be limited to 20. API keys identify clients; concurrency consumes model capacity.

initial_hard_concurrency_limit: 20
max_issued_agent_keys: unlimited_by_model_capacity

The concurrency values must be model/deployment specific. A different model, quantization, topology, context target, or GPU set may receive a different admission envelope.

## 10. Routing and admission policy

### 10.1 Default sequence

For a normal general-purpose Hermes request:

```text
1. Resolve logical model and agent policy.
2. Find healthy local deployments that satisfy context/capability constraints.
3. Apply deployment admission limits.
4. If local capacity is temporarily full, queue for the configured local patience interval.
5. If admitted locally, let the local request continue even if TTFT is slow.
6. Do not start a duplicate OpenRouter request merely because local TTFT is slower than expected.
7. If no local deployment becomes admissible before the queue deadline, and the key permits cloud fallback, use OpenRouter.
8. If local execution actually fails after dispatch and a retry is safe, apply the configured retry/fallback policy.
9. If cloud fallback is disallowed or budget-capped, return an explicit unavailable/capacity response.
```

### 10.2 Initial timeout model

Use separate timeouts for separate failure modes.

Recommended starting configuration, to be benchmark-tuned:

```yaml
routing:
  local_queue_wait_seconds: 120
  local_connection_timeout_seconds: 15
  local_first_token_timeout_seconds: 300
  local_total_request_timeout_seconds: 1200
  cloud_fallback_on_queue_timeout: true
  cloud_fallback_on_slow_ttft_alone: false
  cloud_fallback_on_connection_failure: true
  cloud_fallback_on_local_5xx: policy_controlled
```

The values are intentionally generous because the objective is to use local inference when it is functioning, not optimize for minimum latency at any cost.

Per-model values should replace these defaults once sufficient history exists.
