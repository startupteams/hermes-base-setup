# 0. Mission

Build the first production-usable DKMS slice.

The service must preserve **useful, durable, attributable knowledge** produced by agents and the systems around them without trying to copy every byte of every system into one database.

The most valuable first knowledge classes are:

- approved AI-agent instruction plans;
- final handoffs and durable summaries of handoffs;
- architecture decisions and ADR references;
- Jira scope snapshots and completion summaries;
- work/project trajectory summaries;
- failure signatures, recovery attempts, root-cause findings, side effects, and lessons learned;
- successful remediation/playbook knowledge;
- model/agent evaluation findings that explain why work succeeded or failed;
- selected agent knowledge that should survive runtime/session replacement;
- curated records that may later become training/evaluation data.

The DKMS is **not** a replacement for Jira, GitHub, ACMS, Server Manager, LLM Manager, PDU Manager, Hermes state backup, or service-specific telemetry.

The DKMS is the durable knowledge layer that those systems can write to and retrieve from.

# 5. Security rule: secrets are not knowledge

DKMS must never become a secret dumping ground.

Do not ingest:

- passwords;
- API keys;
- bearer tokens;
- cookies;
- private keys;
- raw credential files;
- environment files containing secrets;
- screenshots or logs that expose secrets.

Knowledge may contain a **secret reference**, credential name, secret-store path, or statement that a credential exists, but not the secret value.

Before a record becomes training-eligible, it must pass secret/sensitive-data checks.

If ingestion detects likely secret material:

```text
reject or quarantine
→ log metadata only
→ mark training_eligibility = deny
→ provide a sanitized-ingestion path
```

Do not echo any secret values from historical source files into Jira, DKMS, logs, prompts, handoffs, screenshots, or Git.

## 6.2 Service boundary

DKMS must be independently deployable from ACMS.

Default MVP:

```text
DKMS service
  Python / FastAPI
  Async SQLAlchemy
  PostgreSQL
  migration-managed schema
  internal REST API
  Markdown import/export
```

Avoid a vector database in the MVP. The current architecture direction explicitly defers vector/semantic indexing until metadata/exact/full-text retrieval proves inadequate.

## 6.3 Hosting and Kubernetes deployment

**User decision:** DKMS gets a **new dedicated virtual machine** and a **dedicated Kubernetes service**. It does **not** belong inside the ACMS container.

```text

          -> DKMS application Deployment/Service
          -> PostgreSQL StatefulSet or equivalently durable Kubernetes-managed database deployment
          -> PersistentVolume-backed data
          -> migration job
          -> backup/export jobs
```

Requirements:

- provision the VM through Server Manager/current placement policy;
- do not hardcode a Proxmox node unless live placement policy requires it;
- do not place by bypassing protected-host rules;
- do not change hostnames;

- cover the VM with PBS according to current backup policy;

- keep Kubernetes manifests/Helm/Kustomize configuration in Git so the service can be recreated;
- design the manifests so they can move to a multi-node cluster later without making multi-node Kubernetes a prerequisite now.

This is an explicit **DKMS-specific exception** to the broader architecture's previous “defer Kubernetes until scale pain” posture. It does not automatically migrate ACMS, Server Manager, LLM Manager, or the agent fleet to Kubernetes.

# 8. Failure learning is a first-class DKMS feature

The architecture workbook explicitly identifies failure/recovery knowledge as high value and potentially useful for future model training.

For each important failure, preserve:

```text
failure signature
failure class
system/service
Work/Jira/agent/session correlation
symptoms
observed evidence
attempted method
attempt number
result
side effects
time to recovery
root cause
final fix
preventive action
rollback used
confidence
validation status
related runbook/playbook
```

## 8.1 Learning lifecycle

Do not let a model promote one guess into permanent truth.

Use:

```text
OBSERVED
→ ANALYZED
→ LESSON_PROPOSED
→ VALIDATED
→ PLAYBOOK_PROMOTED
```

A validated lesson may update a recovery playbook.

The old evidence remains linked and immutable.

## 8.2 Retry learning

The existing direction is:

```text
runtime recovery: up to 5 attempts before Human Attention
failed work reassignment: up to 3 attempts before Human Attention
```

Before retrying failed work, prefer changing in this order:

```text
1. input: instructions / context / implementation strategy
2. brain: model
3. worker: agent
4. human clarification
```

DKMS should make previous attempts retrievable so retries do not blindly repeat the same unsuccessful action.

# 9. Ingestion policy

## 9.1 Human-approved plans

When an approved instruction plan is dispatched:

```text
dispatch Work
AND
asynchronously ingest approved plan into DKMS
```

The ingestion process must not significantly delay dispatch.

Record:

- content hash;
- source filename;
- Work/Jira relationship;
- approval provenance;
- timestamp;
- version/supersession relation.

## 9.2 Final handoffs

On Work completion or explicit handoff:

1. store or reference the source handoff;
2. create a concise durable summary;
3. correlate Jira / Work / agent / session / PR / commit / deployment / artifacts;
4. mark unresolved items;
5. link to the prior plan;
6. retain the summary indefinitely unless policy changes.

## 9.3 Jira

DKMS is **not** a Jira analytics warehouse.

For Jira-backed implementation, retain only enough durable knowledge to reconstruct the implementation trajectory:

- Jira key/title/reference;
- date the work entered execution or was materially scoped;
- short scope/acceptance summary;
- material scope-change summary when it changes architecture/implementation direction;
- date completed/reviewed;
- short outcome/what-was-implemented summary;
- links to relevant plan, handoff, PR/commit/deployment, and DKMS records.

Do **not** continuously copy Jira comments, status history, detailed Work metrics, assignee statistics, or other operational data into DKMS merely because it exists.

The goal is to understand **what changed, when it changed, and how the implementation trajectory evolved** so future agents can infer reasonable next work. Jira remains authoritative for the ticket itself.

## 9.4 ACMS

ACMS should publish knowledge-worthy events, not every heartbeat.

Candidate knowledge-worthy events:

```text
WORK_ACCEPTED              -> optional short implementation-timeline entry
SCOPE_CHANGED              -> only when material
HANDOFF_PUBLISHED          -> durable handoff + summary
WORK_REVIEWED              -> short implementation outcome/timeline entry
WORK_FAILED                -> failure-learning candidate
RECOVERY_EXHAUSTED         -> failure-learning candidate
HUMAN_ATTENTION            -> only when it creates durable lesson/context
LESSON_VALIDATED           -> durable lesson
```

## Authority model

Humans set product intent, approve scope and significant decisions. Agents may inspect, implement approved requirements, write tests, update documentation, create handoffs, and add discoveries to `FUTURE_WORK.md`. Agents must not silently expand scope, accept their own significant ADR, weaken auth/audit, or perform destructive actions.

## Non-negotiable safety rules

1. **Secrets are not knowledge.** Never ingest, store, log, or export password values, API keys, bearer tokens, cookies, private keys, credential-bearing env files, or logs exposing secrets. Ingestion must reject/quarantine likely secret material (`training_eligibility=denied`, metadata only).

3. Records are immutable once created. Corrections happen through new versions + `supersedes` links; old evidence remains.
4. Every write must carry provenance: source kind/URI/UID, agent identity, authority class, scope.
5. Training eligibility defaults: validated internal failure/recovery lessons → `approved`/`auto_policy`/`not_reviewed`; raw transcripts → `denied`; unvalidated inferences → `review_required`; human review state is preserved and never overwritten by later auto-approval.
6. Retention: raw source content = 90 days default; durable summaries/decisions/lessons = indefinite. Purge is policy-driven + audited + dry-run first.
7. Deletion is retention-driven or explicit administrative action with audit. No agent-initiated destructive deletion.
8. Internal LAN only; no public ingress. Never weaken auth to simplify integration.
