# 4. Phase B — Introduce explicit desired-state / power policy

The manager must distinguish:

```text
unexpected outage
```

from:

```text
intentional power saving
```

This is required before automatic VM restart is enabled.

## B1. Add desired-state fields

Add or confirm a persistent per-managed-deployment/per-host state such as:

```text
desired_power_state
    RUNNING
    STOPPED_INTENTIONAL

management_mode
    MANAGED
    UNMANAGED

desired_service_state
    SERVING
    STOPPED
    MAINTENANCE
```

Exact schema naming may differ, but semantics must be explicit.

## B2. Recovery rules

### If:

```text
management_mode = MANAGED
desired_power_state = RUNNING
```

and the VM is unexpectedly stopped:

```text
1. attempt VM start
2. wait for guest agent / network
3. verify service
4. if service is down, perform bounded service recovery
5. verify /v1/models
6. run health completion
7. restore routing only after health passes
```

### If:

```text
desired_power_state = STOPPED_INTENTIONAL
```

then:

```text
do not power on
do not restart the VM
do not route new traffic to it
do not count it as an outage
display "intentionally offline / energy saving"
```

## B3. Required UI controls

For each managed host/deployment provide a clear operator control:

```text
Desired state:
    Online / managed
    Intentionally offline

Current state:
    Running
    Starting
    Loading model
    Healthy
    Failed
    Intentionally off
```

Changing desired state is an audited admin mutation.

## B4. Bounded recovery

Never create an infinite restart loop.

Suggested default:

```text
VM start attempts:       2
service restart attempts: 2
cooldown:                configurable
then:
    mark FAILED
    remove from routing
    alert operator
```

# 10. Phase H — Correct the cost model

The current interface must stop presenting `$0.0000` as though local inference has no cost.

There are multiple different concepts and they must be separated.

## H1. Cost categories

Display at least:

### Provider spend

```text
Actual provider spend
```

For local models:

```text
$0 provider spend
```

is legitimate.

But this is **not** total inference cost.

### Direct compute energy

Primary local metric.

Estimate direct compute power from:

```text
measured GPU watts
+
CPU/platform/RAM overhead estimate
```

Use real GPU telemetry whenever possible.

### Direct compute electricity cost

Primary local cost metric:

```text
direct_compute_kWh * current_electricity_rate
```

### Facility operational energy/cost

Secondary metric:

```text
Emporia whole-compute circuits
cooling
other facility loads
```

Keep cooling separate from the main direct-compute metric.

## H2. Required labels

Never show a calculated value without explaining what it is.

Use labels such as:

```text
Provider spend: ACTUAL
GPU energy: MEASURED
Host overhead: ESTIMATED
Direct compute cost: ESTIMATED
Facility energy: MEASURED (Emporia)
Cooling allocation: MEASURED/ESTIMATED as appropriate
```

## H3. Never fabricate zero

If telemetry is absent:

```text
—
Insufficient telemetry
Coverage incomplete
```

Do not substitute:

```text
$0.0000
```

unless the quantity being displayed is truly known to be zero.

## H4. Telemetry coverage

Every time-based cost/energy total must include telemetry coverage.

Example:

```text
Last 24h direct compute:
5.82 kWh
$0.92 estimated
telemetry coverage: 99.3%
```

If only 60 minutes of samples exist, do not label that result "24h".

## H5. Sanity test the energy integrator

Implement automated tests such as:

```text
100 watts for exactly 1 hour
= 0.100 kWh
```

and:

```text
1000 watts for exactly 1 hour
= 1.000 kWh
```

Fail deployment if the integrator does not pass.

## H6. Rate model

Keep the configured Marion/Alliant seasonal rate components versioned.

Operational planning totals currently include:

```text
winter base energy rate
summer base energy rate
year-round per-kWh fee/rider component
```

Do not collapse the components into an unexplained constant.

## H7. Request-level local cost

When enough telemetry exists, estimate per-request energy cost.

Store:

```text
request_id
model
deployment
start/end
input tokens
output tokens
TTFT
latency
average/attributed watts
estimated Wh
estimated $
confidence
```

If multiple concurrent requests overlap, explicitly use an allocation method and mark the result as estimated.

Do not imply request-level energy is utility-meter exact.

You are not being asked to produce another architecture essay. You are being asked to **modify the existing LLM Manager system and ship a working prototype**.

Use these rules:

1. **Inspect first, then modify.** Read the existing LLM Manager repository, deployment method, services, auth, reverse proxy, database, and UI before changing anything.
2. **Do not create another management VM.** Agent Manager lives on the same VM as LLM Manager and appears as additional navigation tabs/routes in the same infrastructure-management experience.
3. **Do not rewrite working LLM Manager functionality.** Preserve it. Add Agent Manager as a modular subsystem.
4. **Make decisions.** If two approaches are reasonable, choose the simpler reversible approach, record the decision in an ADR, and continue.
5. **Do not ask the human to choose libraries or patterns that you can decide yourself.** Ask only when blocked by missing credentials, unavailable infrastructure, or a destructive decision with material business risk.
6. **Build the vertical slice first.** A single Hermes STEA that can be created and chatted with from the web is more valuable than ten unfinished abstractions.
7. **Keep every change reversible.** Back up the current application/database/configuration before schema or deployment changes. Use migrations. Use feature flags for incomplete adapters.
8. **Commit often.** Create small commits with clear messages after each working milestone.
9. **Measure provisioning.** Human interaction time, clone time, boot time, configuration time, harness readiness, and time-to-first-use must be captured independently.
10. **Leave the system healthier than you found it.** Add health checks, service documentation, backup instructions, and rollback steps.

# 2. Product vision

The LLM Manager and Agent Manager together become the control plane for Startup Teams' local AI infrastructure.

The application should eventually answer these questions from one browser:

- Which local models are online and how much capacity is available?
- Which AI agents exist?
- Which employee or business function owns each agent?
- Which harness and model is each agent using?
- Is an agent online, idle, working, blocked, waiting for review, or unhealthy?
- What project/Jira issue is it working on?
- What plan/instructions was it given?
- What did it change?
- What is waiting for human approval?
- Which agents need attention right now?
- Which agents are using external Frontier models and incurring cost?
- Can I message an agent right now from the browser?
- Can I create another persistent STEA without manually building a VM?

The product is an **operations console first**, not a wall of chat windows.

# 3. V2 fixed product decisions

These are decisions. Do not reopen them during implementation unless technically impossible.

## 3.1 Same VM and unified navigation

- **Do not create a separate Agent Manager VM.**
- Deploy Agent Manager services on the **existing LLM Manager VM**.
- Preserve existing LLM Manager features.
- Add top-level navigation for at least:
  - `Overview`
  - `Models` / existing LLM Manager views
  - `Agents`
  - `Projects`
  - `Plans`
  - `Activity`
  - `Settings`
- A full-page route is acceptable technically; visually it must feel like another tab/module in the same product.
- Use the same hostname, TLS boundary, and authentication entrypoint where practical.

## 3.2 Modular implementation, not a monolith rewrite

Preferred deployment shape on the existing VM:

```text
Browser
  |
  v
Existing Reverse Proxy / Unified Web Entry
  |
  +--> Existing LLM Manager UI/API
  |
  +--> /agents, /projects, /plans, /activity
          |
          +--> Agent Manager UI
          +--> Agent Manager API
                 |
                 +--> PostgreSQL
                 +--> job worker
                 +--> Proxmox adapter
                 +--> LLM Manager adapter
                 +--> LLDAP adapter
                 +--> Jira adapter
                 +--> integration/tool adapters
                 +--> agent runtime gateway
```

Do not force Agent Manager into the same process if that creates unnecessary coupling. Sharing the VM, auth entry, navigation, and user experience is sufficient.

## 3.3 Technology choice

Unless the existing LLM Manager already has an equivalent, stable stack that can be extended cleanly, use:

- Backend: Python 3.12 + FastAPI
- Database: PostgreSQL 16
- ORM/migrations: SQLAlchemy 2 + Alembic
- Background jobs: Redis + Celery or RQ; choose Celery if neither exists already
- Frontend: React + TypeScript
- Realtime: SSE first; WebSocket only where bidirectional streaming materially improves chat
- Proxmox: REST API, preferably `proxmoxer`
- Tests: pytest + Playwright
- Telemetry: OpenTelemetry-compatible event/trace design
- Deployment: Docker Compose on the existing LLM Manager VM if Docker is already acceptable there; otherwise systemd services

**Rule:** reuse the existing frontend framework and reverse proxy if doing so is materially faster than introducing a second frontend build system.

## 3.4 Persistent STEA model

- A **STEA** is primarily one persistent VM per employee.
- The VM is a company asset associated with that employee's role.
- The purpose is not merely to answer questions. The STEA should learn approved role context and eventually be able to continue the employee's responsibilities when the employee is unavailable.
- An employee may temporarily use another available STEA as a worker bot, but that does not change primary ownership.

## 3.5 Harnesses

The harness selector must have these values:

- `HERMES`
- `PI`
- `RUFLO`
- `OPENCLAW`

Implementation order:

1. Hermes — production-capable prototype first.
2. Pi — experimental adapter.
3. Ruflo — experimental adapter, using `https://github.com/jordatech/ruflo` as the Startup Teams-controlled reference fork.
4. OpenClaw — experimental adapter.

The UI may show Pi/Ruflo/OpenClaw as **Experimental** until their acceptance tests pass, but the data model and adapter interface must support all four from the start.

## 3.6 Human interface

- **Web is the primary interface.**
- Telegram is optional, not the primary V2 employee interface.
- Every accessible agent must have an Agent Detail page with a browser-based chat/session surface.
- The UI should deliberately borrow successful patterns from open-source agent dashboards instead of inventing everything from scratch.

Design references:

- Hermes Studio — per-agent chat, session history, tool activity, approvals, skills, schedules, crews.
- Paperclip — agent-as-employee organization, task/project flow, approvals, budgets, agent ownership.
- Mission Control — fleet operations, status, tasks, logs, cost, alerts, runtime adapters.
- Agent Board / ClauBoard / Lattice — optional references for Kanban, DAG, and visual dependency views.

Do not copy an entire backend simply because the UI looks good. Reuse MIT-licensed UI code/components only when it saves time and attribution is preserved.

## 3.7 Creation-time target

Measure two different numbers:

**Human setup time:**
- Target: **< 5 minutes** of human work.
- The user should not need to SSH, edit YAML, or manually install packages.

**Machine time to usable agent:**
- Target: **< 15 minutes p95** from clicking `Provision` to successful web conversation.
- Absolute prototype maximum: **30 minutes**.
- Optimize later toward <5 minutes machine time, but do not hold the prototype hostage to that goal.

## 3.8 Default autonomy: YOLO development profile

Create a default guardrail profile named:

`STEA_YOLO_DEV_V1`

Default allowed actions:

- read/write/delete files inside assigned workspaces;
- shell commands;
- install packages;
- clone repositories;
- create branches;
- edit code;
- run tests;
- run build tools;
- commit changes;
- push branches where credentials permit;
- create pull requests;
- use approved web/browser/research tools;
- send approved email, Slack, Telegram, and Jira comments where connectors permit;
- create/update Jira work metadata when permitted;
- call local LLMs;
- call external models according to routing policy;
- create artifacts and reports.

Human gates:

- **Merge requires human approval.**
- **Production deployment requires human approval.**

Always required even in YOLO mode:

- audit logging;
- secret redaction in logs/UI;
- attribution of agent actions;
- hard emergency stop;
- resource limits;
- explicit model/tool identity in execution records.

## 3.9 Authentication and access

LLDAP is mandatory in the first prototype.

Rules:

- Authenticate normal users through existing LLDAP.
- Maintain a local emergency `root`/break-glass login if LLDAP is unavailable, matching the LLM Manager pattern.
- When an LLDAP user creates a STEA, grant equivalent normal access to:
  1. the creating LLDAP user;
  2. LLDAP user `jordatech`;
  3. local emergency/root authority.
- Normal users listed on an agent have the same practical agent access: read history, chat, assign work, inspect artifacts, and view activity.
- `root` has global audit/override access to all agents whether explicitly listed or not.
- Do **not** give managers automatic visibility into other employees' STEAs in V2.
- All access changes must be audited.

Use an `agent_access` join table. Do not encode access only inside free-form configuration files.

## 3.10 Information-overload rule

The default dashboard must show **exceptions and summaries**, not raw firehoses.

At fleet scale, prioritize:

1. blocked agents;
2. failed agents;
3. review-ready work;
4. agents waiting for a human;
5. external-model spend anomalies;
6. unhealthy VMs/harnesses;
7. stale work;
8. high-priority active work;
9. completed work summaries.

Raw logs and full chats belong behind drill-down/search.

## 3.11 Model strategy

Default policy: `LOCAL_FIRST`.

Worker STEAs/STBMs:
- use a local LLM profile from LLM Manager by default;
- prefer the high-concurrency local Qwen-class worker profile where suitable.

Supervisor/orchestrator agents:
- may use a Frontier model by default for planning/review when explicitly configured;
- GLM 5.3 Flash is an acceptable example Frontier supervisor;
- local Frontier-class models remain an option.

Escalation to Frontier model may occur when:

- the task is marked `REVIEW_REQUIRED`;
- a worker fails the same objective twice;
- a supervisor is requested;
- a project policy explicitly selects Frontier;
- the local model reports a hard context/capability limitation;
- code review or architecture review policy requires it.

Record all external-model calls and estimated cost.

**Do not invent a data-egress policy yet.** Create a prominent unresolved governance item because the product owner has not yet defined which information may never leave local infrastructure.

## 3.12 DeepAPI policy

Use DeepAPI as a preferred tool provider where its current capabilities fit, especially:

- web search;
- deep research;
- structured website/GitHub/PDF extraction;
- professional contact discovery/verification;
- email outreach;
- browser actions;
- hosted agent memory where appropriate.

Do **not** assume DeepAPI provides Jira, Slack, Telegram, Google Calendar, or every business integration.

Implement tool integrations through an adapter/connector interface so DeepAPI can be replaced or supplemented later.

# 4. Architecture: control plane + per-agent gateway

## 4.1 Central control plane

Agent Manager on the LLM Manager VM owns:

- identities and access;
- agent definitions;
- desired state;
- Proxmox placement/provisioning;
- harness selection;
- LLM profile selection;
- project/task assignments;
- Jira links;
- Plan Artifacts;
- chat/session index;
- run history;
- approvals;
- model/tool usage summaries;
- provisioning logs;
- audit events;
- fleet health.

## 4.2 `st-agentd` inside each agent VM

Create a small Startup Teams agent-side daemon named `st-agentd`.

Purpose: give the central manager one stable interface regardless of harness.

Minimum responsibilities:

- heartbeat;
- harness health;
- expose harness/version/model metadata;
- receive a task packet;
- start/continue/cancel a harness session;
- stream normalized events;
- return session metadata;
- return summarized tool activity;
- expose workspace/artifact references;
- restart harness service;
- report CPU/RAM/disk basics;
- support graceful export of agent configuration for future migration.

Suggested API:

```text
GET  /health
GET  /runtime
GET  /sessions
POST /sessions
POST /sessions/{id}/messages
POST /tasks
GET  /tasks/{id}
POST /tasks/{id}/cancel
GET  /events/stream
POST /runtime/restart
GET  /export-manifest
```

Use mutual trust suitable for the LAN environment: at minimum a unique per-agent scoped token stored encrypted centrally and root-readable locally. Prefer mTLS later.

Never expose `st-agentd` directly to the public internet.

# 6. Proxmox provisioning strategy

## 6.1 VM isolation

- Persistent STEAs use **QEMU VMs** in the first implementation.
- LXC remains a future optimization for worker fleets.
- Do not redesign the cluster to support 1,000 VMs during V2.

## 6.2 Golden templates

Use a base Ubuntu 24.04 Cloud-Init image plus harness-specific template builds.

Create automated template builder/versioning for:

- `STEA-HERMES-UBU2404-v1`
- `STEA-PI-UBU2404-v1`
- `STEA-RUFLO-UBU2404-v1`
- `STEA-OPENCLAW-UBU2404-v1`

Build Hermes first.

Templates include:

- Ubuntu Server 24.04 LTS;
- qemu-guest-agent;
- `st-agentd`;
- standard system packages;
- Git;
- Python/Node tooling required by the harness;
- harness pre-installed but **not** containing employee secrets;
- systemd unit definitions;
- logging/telemetry agent;
- Cloud-Init readiness.

Provisioning should be mostly clone + inject config + boot + validate, not install-everything-from-internet.

## 6.3 Placement

Define configuration:

`AGENT_COMPUTE_NODES=<comma separated approved Proxmox nodes>`

The control plane chooses the approved node with sufficient free memory/disk and lowest configured load score.

Do not silently provision onto arbitrary cluster nodes outside the allowlist.

## 6.4 VM naming

Use deterministic hostnames:

`stea-<short-user>-<agent-short-id>`

Example:

`stea-alex-7f2c`

Store Proxmox VMID separately from public agent UUID.

# 7. Create Agent wizard

The primary workflow must be a wizard that an ordinary authorized user can complete quickly.

## Step 1 — Identity

Fields:

- display name;
- agent type: `STEA` or `STBM`;
- employee/owner LLDAP user;
- optional role title;
- optional role-description file/link;
- optional description.

For STEA, preselect current logged-in user as owner.

## Step 2 — Runtime

Fields:

- harness: Hermes / Pi / Ruflo / OpenClaw;
- template version;
- resource preset: Small / Standard / Large;
- placement = Auto by default.

## Step 3 — Model routing

Fields:

- local worker model profile from LLM Manager;
- routing policy = `LOCAL_FIRST` default;
- optional supervisor/reviewer model;
- optional external budget limit.

## Step 4 — Tools and work context

Fields:

- repository URLs;
- Google Drive / internal resource references if applicable;
- DeepAPI enabled/disabled;
- Jira project/issue link;
- communication connectors;
- optional skills/toolsets;
- default workspace instructions.

## Step 5 — Instructions / Plan

Allow:

- select an existing Plan Artifact;
- upload one or more `.md` files;
- add notes explaining what each file is and how the agent should use it;
- optionally link each file to a Jira issue;
- choose one Plan Version as the initial active instruction set.

## Step 6 — Review and Provision

Show:

- ownership/access;
- VM resources;
- harness;
- local/frontier model policy;
- tools;
- Jira linkage;
- plan files;
- human gates;
- expected estimated provisioning time.

One `Provision` action starts the job.

# 8. Plan Artifact subsystem

This is a core V2 feature.

## 8.1 Purpose

Users may create implementation plans in ChatGPT or elsewhere and upload Markdown as instructions for an agent, supervisor, or project.

Do not treat these as anonymous file attachments.

## 8.2 Entities

### `plan_artifacts`

- `id`
- `title`
- `slug`
- `description`
- `project_id` nullable
- `jira_issue_id` nullable
- `created_by_user_id`
- `created_at`
- `status`: `DRAFT`, `ACTIVE`, `SUPERSEDED`, `ARCHIVED`

### `plan_versions`

- `id`
- `plan_artifact_id`
- `version_number`
- `original_filename`
- `markdown_body`
- `sha256`
- `change_note`
- `usage_instructions`
- `created_by_user_id`
- `created_at`

### `plan_attachments`

For non-Markdown support later:

- metadata only in V2 if not needed immediately;
- keep binary/object storage as a future extension.

## 8.3 Storage decision

For the prototype:

- store Markdown body directly in PostgreSQL;
- store metadata, notes, checksum, and versions in PostgreSQL;
- enforce a sensible Markdown upload limit such as 2–5 MB;
- preserve the original filename;
- sanitize rendered HTML;
- support full-text search later.

Do not add MinIO/S3 solely for Markdown V2.

## 8.4 Version semantics

- Never overwrite a Plan Version used by a run.
- Editing creates a new version.
- Every task/run stores the exact `plan_version_id` it received.
- UI must show `Used by N runs` and linked Jira issues.

## 8.5 Task packet

When work is dispatched, create an immutable task packet containing:

- agent ID;
- project ID;
- Jira issue key and a captured Jira summary/description snapshot when available;
- Plan Version(s);
- explicit usage instructions for each plan;
- repository/workspace links;
- acceptance criteria;
- human approval rules;
- model routing policy;
- assigned supervisor if any;
- timestamp and initiating principal.

This packet is the auditable record of what the agent was told to do.
