```text

```

For six 3080s, test topology conservatively.

## Candidate A — TP2 × PP3 + EP

Preferred first hypothesis:

```text
TP = 2
PP = 3
DP = 1
EP = enabled
MTP = off
all 6 GPUs
```

Why:

- model has 2 KV heads, making TP2 natural;
- PP distributes layers over all six GPUs;
- DP1 avoids three model/PLE copies;
- 20 GB cards have less per-GPU VRAM than the reference 24 GB 3090s, so PP3 may help per-stage fit.

This is **not yet a validated published topology**.

Before a long startup, verify that the pinned patchset accepts `pipeline_parallel_size=3`.

If PP3 requires extensive new source changes, stop and move to Candidate B rather than creating a large custom fork.

## Candidate B — TP1 × PP6 + EP

If supported cleanly:

```text
TP = 1
PP = 6
DP = 1
EP = enabled
```

This distributes layers even more finely.

Trade-offs:

```text
more pipeline bubbles
less tensor communication
potentially easier VRAM fit
more pipeline-stage complexity
```

Test only if the selected vLLM patchset supports the stage count without invasive changes.

## Candidate C — TP2 × PP2 on four GPUs

Use the published topology as a **recipe-fidelity control**.

```text
TP = 2
PP = 2
4 GPUs active
2 GPUs idle
```

Because RTX 3080 cards have 20 GB rather than 24 GB, this may fail from per-GPU VRAM pressure.

Its purpose is diagnostic:

If Candidate C works but six-GPU variants fail, the problem is topology adaptation, not the basic model/runtime.

This is deliberate — it prevents an LLM from flipping the toggle on itself mid-task.\n\n2. **Secret redaction is OFF by default** — Tool output passes through unmodified. This does NOT affect `approvals.mode` — they are independent settings.\n\n3. **YOLO mode is NOT safe for secrets** — Setting `approvals.mode: off` or `--yolo` disables command approval but does NOT disable secret redaction. These are independent controls.\n\n4. **Toolset changes don't apply mid-conversation** — Enabling/disabling toolsets takes effect on `/reset` (new session) only. They do NOT apply mid-conversation to preserve prompt caching. Tell users this explicitly.\n\n5. **Cron jobs run in a fresh session** — Cron cron-run sessions have no current-chat context. Prompts must be fully self-contained. Skills and context_from are the only way to inject prior state.\n\n6. **Script-based cron jobs expect scripts in the profile's scripts/ directory** — Not `~/.hermes/scripts/`. The scheduler looks for scripts at `~/.hermes/profiles/<profile>/scripts/<name>.sh`.\n\n7. **tmux sessions persist after Claude Code exits** — If Claude Code crashes or is killed mid-session, the tmux session remains. Use shell redirect (`> output.md 2>&1`) or the `write_file` tool instead.\n\n10. **Fable 5 session token budget** — Fable 5 has a per-session token budget. Running multiple parallel Fable 5 jobs can exhaust the budget mid-run. Run them sequentially or with max 2 concurrent.\n\n11. **Session resumption requires same directory** — `--continue` only works in the same working directory. For cross-directory work, capture the session ID and resume explicitly.\n\n12. **Context degradation is real** — AI output quality measurably degrades above 70% context window usage. Monitor with `/context` and proactively `/compact`.\n\n13. **`/exit` opens agent selector in OpenCode** — It's NOT a valid exit command.
