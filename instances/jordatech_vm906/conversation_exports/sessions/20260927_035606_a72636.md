## 3. Deployment authority model

Use this workflow:

```text
feature branch
   ↓
pull request
   ↓
human review
   ↓
merge to main
   ↓
human authorizes deployment
   ↓
AI agent deploys approved main commit
   ↓
automated validation
   ↓
SUCCESS → release stays live
   ↓
FAILURE → AI agent automatically rolls back
```

A deployment is a human-gated action.

Once a human explicitly authorizes deployment of a specific merged release, **rollback to the immediately previous known-good release is pre-authorized as a safety action** if validation fails.

The rollback agent does not need to wait for a second human approval merely to return the service to the exact pre-deployment state.

The agent must stop and request human direction if it cannot prove that the previous state can be safely restored.

## 5. Pre-deployment database backup

Before every production deployment that may run migrations, create a PostgreSQL backup.

Recommended:

```bash
pg_dump -Fc
```

Store backups under:

`/opt/acms/releases/backups/`

The deployment agent must:

1. create the backup;
2. verify the command succeeded;
3. verify the file is non-empty;
4. calculate a SHA-256 checksum;
5. record the checksum in deployment metadata;
6. refuse migration if backup validation fails.

Suggested retention:

- keep at least the most recent 10 deployment backups;
- never delete the only backup associated with the current or previous known-good release;
- PBS/Proxmox backups remain the disaster-recovery layer.

## 6. Deployment maintenance window

To make automatic database rollback safe, prevent new ACMS writes between the pre-deployment backup and successful completion of post-deploy validation.

For the MVP, use a short maintenance window:

1. put the UI into maintenance mode or stop ACMS application writes;
2. create the pre-deploy PostgreSQL backup;
3. build/select the target image;
4. run Alembic migrations;
5. start the target application;
6. run validation;
7. if validation succeeds, exit maintenance mode;
8. if validation fails, keep maintenance mode enabled and execute rollback.

A brief internal outage is preferable to complex zero-downtime deployment at this stage.

## 7. Safe release transaction

Enhance `deploy/update.sh` or add:

`deploy/release.sh`

### Phase A — preflight

Verify:

- target commit is part of approved `origin/main`;
- production working tree has no uncommitted changes;
- PostgreSQL is healthy;
- current ACMS health is good before deployment;
- disk space is sufficient;
- target image builds successfully;
- migration graph is valid;
- required secrets exist;
- previous release metadata can be determined.

If preflight fails, do not modify the live release.

### Phase B — preserve old state

Record old Git SHA, old image, and old Alembic revision.

Enter maintenance mode / stop writes.

Create and validate PostgreSQL backup.

### Phase C — deploy

- checkout approved target SHA;
- build/tag target image;
- run `alembic upgrade head`;
- start target app;
- reload proxy if necessary.

### Phase D — validate

If all required validation passes:

- mark release successful;
- update `current` and `previous`;
- exit maintenance mode;
- preserve pre-deploy backup;
- write deployment handoff.

If validation fails:

**automatically invoke rollback.**

## 8. Rollback strategy

Use the lowest rollback level that reliably returns ACMS to a known-good state.

### Level 0 — service restart

Use when code/schema did not change and the failure appears transient.

Action:

- restart failed service/container;
- rerun smoke tests.

### Level 1 — application-only rollback

Use when:

- the application release is broken;
- migration did not run, or the schema is known to remain backward-compatible;
- there is no evidence of data corruption.

Action:

1. stop failed application;
2. switch to previous Git SHA / previous Docker image;
3. start previous app;
4. run smoke tests;
5. verify LLDAP login;
6. verify registered agents/work data.

Do not run Alembic downgrade automatically.

### Level 2 — application + database restore

Use when:

- failed release ran a migration;
- compatibility with previous app cannot be proven;
- migration partially failed;
- schema/data state is suspicious;
- post-deploy validation fails after migration.

Because deployment is under maintenance mode, restoring the pre-deploy backup should return the system to the exact previous state.

Sequence:

1. keep ACMS stopped / maintenance active;
2. verify pre-deploy dump exists;
3. verify checksum;
4. record failed Git SHA and DB revision if readable;
5. terminate active ACMS database connections;
6. recreate/restore ACMS database from pre-deploy dump;
7. switch to previous known-good app image/SHA;
8. start previous ACMS;
9. verify previous Alembic revision;
10. run complete smoke test;
11. verify LLDAP login path;
12. verify expected core data exists;
13. exit maintenance mode only after validation succeeds;
14. record rollback in release history.

The rollback script must refuse database restore unless:

- a valid pre-deploy backup exists;
- checksum validation succeeds;
- the backup belongs to the current deployment transaction;
- the deployment has not already been accepted and reopened for normal writes.

If any guard fails, stop and request human direction.

### Level 3 — VM/PBS disaster recovery

Use when:

- PostgreSQL volume is damaged;
- Docker/host state is corrupted;
- automated DB restore fails;
- filesystem damage occurred;
- VM cannot boot;
- previous release cannot be recovered locally.

Recovery:

1. isolate/offline the failed VM;
2. restore latest known-good ACMS VM from Proxmox Backup Server;
3. boot restored VM;
4. verify Git SHA / ACMS version;
5. verify PostgreSQL;
6. run smoke tests;
7. verify LLDAP login;
8. confirm agent/work data.

Do not destroy the failed VM until recovery is verified.

## 10. Automatic rollback triggers

Automatically rollback before release acceptance if any of these occur:

- `/health` fails;
- database connectivity fails;
- Alembic migration fails;
- app container repeatedly crashes;
- HTTPS proxy cannot reach ACMS;
- access controls fail;
- expected API route returns fatal errors;
- UI login page fails;
- required work/agent pages fail;
- migration revision differs from expected;
- smoke tests fail;
- app startup times out.

If automated tests pass but the human reports a severe regression immediately after deployment, the human may instruct:

`rollback ACMS`

and the agent should rollback instead of attempting speculative live repair first.

## 29. Rollback prohibitions

The rollback agent must never:

- guess the previous release;
- blindly run `alembic downgrade`;
- delete the only verified backup;
- restore a dump with failed checksum;
- serve writes during database restore;
- rewrite Git history;
- patch production code directly;
- deploy an unreviewed branch as a permanent fix;
- hide a failed rollback;
- destroy the failed VM before recovery is verified.

A corrective PR fixes `main` later.

## 30. Recovery layers

Use three separate layers:

### Git
Source history and previous application versions.

### Pre-deploy PostgreSQL dump
Fast deterministic app/database rollback.

### Proxmox Backup Server
Whole-VM disaster recovery.

Do not treat any one layer as a substitute for the others.

## 1. Goal

Combine the former heartbeat/live-status slice and A2A delivery/steering slice into one useful vertical feature.

At completion ACMS should be able to:

- distinguish bridge/connectivity health from whether the harness is actively running an agent turn;
- know the ACMS Work Item/Assignment that was approved;
- know the harness session ID/title and what the agent appears to think it is doing;
- correlate those two views through immutable ACMS identifiers;
- receive a full lightweight status heartbeat every 60 seconds;
- mark connectivity stale after 5 minutes without contact;
- actively reconcile after 1 continuous hour stale;
- reconcile every registered agent at least every 24 hours;
- monitor context-window use and warn before exhaustion;
- send work, steering, pause, resume, interrupt, and cancel when the harness has proven support for the required semantics;
- record important state/control changes as semantic events;
- request a Markdown handoff if the reported session persistently disagrees with the approved assignment;
- show all of this in the existing ACMS UI.

This is the point where ACMS begins acting as a real workforce control plane instead of only a management database.

### ACMS-REQ-052 - Human-readable work and assignment correlation identifiers

ACMS shall assign immutable human-readable identifiers to Work Items and primary assignments and communicate them to the executing bridge/harness.

Acceptance:

- Work Item has a unique immutable human-readable key plus its UUID.
- Assignment has a unique immutable human-readable key plus its UUID.
- keys are never reused;
- work key is communicated during work dispatch;
- assignment key is included in structured task/control metadata;
- session/title information can be compared with expected ACMS work;
- a later Jira/GitHub reference can coexist without replacing the ACMS key.

### ACMS-REQ-053 - Session/work alignment and drift detection

ACMS shall compare the agent's reported session/work identity to its approved primary assignment.

Acceptance:

- heartbeat contains session ID/title when available;
- ACMS knows expected work/assignment keys;
- ACMS derives `ALIGNED`, `UNKNOWN`, or `MISMATCH`;
- mismatch does not change approved scope;
- persistent mismatch can request a handoff;
- discrepancies are auditable.

### ACMS-REQ-054 - Context-window telemetry and warning

ACMS shall collect available current-context usage and display used tokens, maximum tokens, and utilization percentage.

Acceptance:

- current context usage is separate from lifetime/cumulative API usage;
- invalid values are not treated as valid counts;
- warning level is visible;
- explicit context-overflow/provider failures can be recorded as events.
