# 2. Why SR-IOV is preferable to passing both physical functions into VM109

Passing both physical ConnectX-5 PF functions directly to VM109 is conceptually possible in an ordinary PCI-passthrough design, but it is not the preferred architecture here for several reasons.

## 2.1 Existing hardware evidence already warns against it

The prior MARION qualification found that handing both functions of the same dual-port CX5 to VFIO/QEMU can wedge the card in a D3cold / invalid-interrupt state and may require a Proxmox-host reboot to recover.

Do not repeat that experiment as part of this plan.

## 2.2 It transfers ownership of both physical ring links away from the host

If both PFs are assigned to VM109:

```text
MIAM-00143 host loses both CX5 ports
VM109 becomes the owner of both physical links
```

That means:

- Proxmox cannot directly monitor/use those PFs.
- Host-level RDMA qualification disappears for those links.
- VM109 must be running and healthy for anything implemented through its networking stack.
- A VM restart or guest-network problem changes the physical-network control plane.

SR-IOV instead leaves the PF and physical link under the host while exposing a hardware-backed VF to the VM.

## 2.3 Making VM109 a router is not the same as giving all three inference VMs direct RDMA

The physical ring legs terminate on the physical ConnectX-5 ports.

Today:

```text
111 <-> 143 leg terminates on host PFs
143 <-> 144 leg terminates on host PFs
111 <-> 144 leg has the known guest PF-passthrough path
```

Putting both 143 PFs inside VM109 would make VM109 an endpoint on those two links, but VM103 and VM111 would still need access to their corresponding physical 111/144 ring ports to create a true guest-to-guest RDMA triangle.

A Linux router can forward ordinary IP traffic, and RoCEv2 is IP-routable in principle, but that becomes a routed software topology rather than the simple direct NIC-to-NIC guest RDMA topology we want. It adds:

- routing configuration
- additional failure dependencies
- extra latency/CPU work
- more complicated NCCL interface selection
- more complicated MTU/PFC/ECN troubleshooting
- loss of the simple one-link-per-neighbor topology

The preferred design is therefore **direct hardware-backed VFs on each physical leg**.

# 11. Phase 5 — design the full guest-side triangle

After VM109 VF-RDMA is proven, evaluate two migration strategies.

## Strategy A — hybrid minimal-change design

Keep the existing physical PF passthrough on leg C:

```text
VM103 <-> VM111 leg C stays physical-PF passthrough
```

Add SR-IOV VFs on the host-owned ring PFs:

```text
MIAM-00111 host PF toward 143 -> VF passed to VM103
MIAM-00143 PF toward 111      -> VF passed to VM109
MIAM-00143 PF toward 144      -> VF passed to VM109
MIAM-00144 host PF toward 143 -> VF passed to VM111
```

This produces guest access to all three physical legs with the fewest changes.

### Concern to investigate

111 and 144 currently have a split-driver card state:

```text
one PF -> vfio/QEMU
sibling PF -> mlx5_core host
```

The environment has prior evidence of card-state instability involving dual-function VFIO.

Before creating VFs on the host-owned sibling PF of 111 or 144, explicitly test whether SR-IOV VF creation remains stable when the other PF is passed through.

Do not assume this is safe.

## Strategy B — recommended long-term symmetric design

Convert all three cards to:

```text
PF0 -> host mlx5_core
PF1 -> host mlx5_core
VF from PF0 -> inference VM
VF from PF1 -> inference VM
```

Then:

```text
VM103: 2 VFs
VM109: 2 VFs
VM111: 2 VFs
```

Advantages:

- all three physical cards stay host-controlled
- no physical PF bound to vfio
- eliminates mixed PF/vfio state on the same card
- symmetric configuration across all three servers
- each inference VM has a direct VF to both neighbors
- host can still monitor/benchmark the same physical links
- easier future automation

Disadvantages:

- requires changing the already-working 111<->144 guest PF-passthrough path
- must be performed in a maintenance window
- requires proving VF RDMA performance is close enough to current PF-passthrough performance

### Recommendation

Use Strategy A only as an intermediate proof if it is stable.

If VF RDMA performs well, **Strategy B is the cleaner final architecture**.
