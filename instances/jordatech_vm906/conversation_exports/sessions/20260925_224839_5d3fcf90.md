# AGENTS.md

Instructions for autonomous and semi-autonomous agents working in ACMS.

## Authority model

Humans set product intent, approve scope, approve significant decisions, define mandatory governance boundaries, and approve merges.

Agents may inspect the repository, plan, implement approved requirements, decompose approved scope into tasks, create tests, update affected documentation, create handoffs, add out-of-scope discoveries to `FUTURE_WORK.md`, draft ADRs/TDRs, and execute non-destructive work inside explicitly approved scope/budget/security/environment boundaries.

Agents must not silently add/remove product scope, promote future work, accept their own new significant ADR, merge their own feature work, exceed a budget, cross tenant/context boundaries, deploy to production, alter credentials/permissions, perform destructive infrastructure actions, or modify protected Organization/Product/Project/Feature context without required human authorization.

## Read before planning

For every meaningful change read:

1. `README.md`
2. `REQUIREMENTS.md`
3. `SPRINT.md`
4. `docs/BUSINESS_PROBLEMS.md`
5. `docs/ARCHITECTURE.md`
6. relevant accepted/proposed ADRs
7. `FUTURE_WORK.md` when scope/follow-up work is involved
8. `INITIAL_IDEAS.md` when source provenance matters

## Requirement discipline

Implementation must trace to one or more `ACMS-REQ-###` entries. Before editing summarize the requirement IDs, acceptance criteria, files/components likely to change, assumptions, and validation.

If work is outside approved requirements, ask for human approval or record it in `FUTURE_WORK.md`.

## Future-work provenance

Every future-work item must identify one of:

- **Human-Directed**
- **Agent-Discovered**
- **Source-Derived**

Human-Directed does not mean approved; it remains future scope until promoted.

## Centralized governance, decentralized execution

ACMS controls approved assignment, scope, budget, context access, permissions, and governance. It must not become the synchronous permission service for every shell command/tool call/test/retry.

A worker agent may autonomously execute implementation details inside its approved envelope.

An agent may have:

- one primary ACMS work assignment; and
- zero or more registered background routines/cron jobs.

## Context authority

Protected context levels:

- Organization
- Product

`feat/ACMS-001-control-plane-scaffold`

The approved direction is:

- Python is the default language for the ACMS backend, agent integrations, service tooling, evaluation, and automation **unless a measured reason justifies another language**.

## 2. Architecture intent

The reason for this decision is **product iteration speed**.

ACMS is still discovering the correct product behavior, workflow model, agent-management model, context model, and human-control experience. The architecture should therefore optimize for:

1. rapid implementation and modification by AI coding agents;
2. easy access to the Python AI/LLM ecosystem;
3. clear contracts and tests that preserve the option to rewrite individual services in Go/Rust later if measurement justifies it;
4. avoiding premature optimization for extreme scale;
5. keeping durable contracts more stable than the implementation language.

Do not make "Python everywhere forever" a hard constraint. Record the intended rule:

> Use Python for ACMS backend services, agent integration, tooling, evaluation, and automation unless measurements or a concrete architectural need justify another language.

Potential future high-throughput components such as an external agent gateway, event-ingest service, or Agent Bridge may later be rewritten in Go or Rust without changing the ACMS domain model or A2A-facing contracts.

`docs/adr/0007-mvp-implementation-stack.md`

### 3.1 Change status

Change `Status: Proposed` to `Status: Accepted`.

This decision was explicitly approved by the human product owner during the 2026-09-25 ACMS architecture co-work session.

### 3.2 Record the accepted stack

The ADR should clearly record:

- Python 3.12+;
- FastAPI;
- Pydantic;
- SQLAlchemy 2.x async API;
- `asyncpg` for PostgreSQL;
- PostgreSQL for normal development, integration testing, and deployment;
- SQLite only for isolated/unit tests where appropriate;
- `aiosqlite` if asynchronous SQLite-backed tests are retained;
- Alembic for schema migrations;
- pytest;
- A2A as the primary agent communication semantic foundation;
- official A2A Python SDK preferred when A2A code is introduced;
- HTTP+JSON and SSE as the initial MVP transport/streaming path;
- temporary private-network bearer-token authentication behind a replaceable auth boundary.

### 3.3 Record the language/rewrite principle

Add a consequence or architecture principle explaining:

- Python was selected primarily to maximize iteration speed and AI-agent maintainability.
- ACMS protocol contracts, API schemas, database migrations, event semantics, and automated tests should be documented well enough that performance-sensitive components can later be reimplemented in another language without redefining ACMS behavior.
- Rust/Go are future optimization options, not current MVP requirements.
- Rewrites must be driven by measured bottlenecks or a concrete operational need.

### 3.4 Remove obsolete wording

Remove the existing consequence that says synchronous SQLAlchemy is intentionally simple and may later be replaced.

Async persistence is now part of the approved MVP foundation.

## 4. Rewrite PR #1 database persistence to async

The current branch uses synchronous SQLAlchemy in at least:

- `acms/db.py`
- `acms/main.py`
- `acms/registry.py`

Revise this now, before PR #1 is merged.

### 4.1 `acms/db.py`

Replace the synchronous engine/session pattern with SQLAlchemy 2.x async equivalents:

- `create_async_engine`
- `async_sessionmaker`
- `AsyncSession`

Use async-compatible database URLs:

- PostgreSQL: `postgresql+asyncpg://...`
- SQLite test use: `sqlite+aiosqlite:///...`

Keep database setup centralized. Do not duplicate engine/session creation across modules.

### 4.2 `acms/main.py`

Convert database-dependent FastAPI routes/dependencies to async operation.

- Database dependency yields `AsyncSession`.
- Database-backed handlers use `async def`.
- Remove application-startup/import schema creation such as `Base.metadata.create_all(...)`.

Development/deployment schema evolution must be performed through Alembic migrations, not runtime `create_all()`.

### 4.3 `acms/registry.py`

Convert persistence operations to async SQLAlchemy while preserving behavior.

Preserve at least:

- new registration creates a durable ACMS identity;
- re-registering an existing `external_registration_id` preserves the same ACMS `agent_id`;
- bridge/capability information updates;
- listing has deterministic ordering;
- commits/refreshes are awaited;
- errors are not silently swallowed.

Do not alter public API semantics merely to perform the async conversion.

### 4.4 Models

Keep the existing SQLAlchemy declarative model unless change is necessary for async compatibility. Do not redesign the agent model as part of this task.
