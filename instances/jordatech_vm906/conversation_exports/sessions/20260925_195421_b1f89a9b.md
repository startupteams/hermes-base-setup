- Treat the deployed LLM Manager as production.
- This task is **capture/documentation**, not a refactor sprint.
- Do not modify production code merely to make the repository prettier.
- Do not commit secrets, production database contents, venvs, model weights, large caches, logs, or private keys.
- Preserve exact deployed behavior first; refactoring belongs in a later approved sprint.
- Human review is required before merge.

1. Check for an existing approved issue covering “capture deployed LLM Manager service + bootstrap project framework.”

```text

```

On VM114 / the deployed LLM Manager system, inventory **read-only** before copying.

Discover rather than assume:

```bash
pwd
systemctl list-units --type=service --all | grep -Ei 'llm|lite|nginx|recovery|manager'
ps -ef | grep -Ei '[l]lm|[l]itellm|[u]vicorn|[g]unicorn'
find /opt/llm-manager -maxdepth 3 -type f 2>/dev/null | sort
```

Expected historical locations include `/opt/llm-manager/app`, `/opt/llm-manager/control`, and `/opt/llm-manager/collectors`, but the live system is authoritative.

Record:

- application source directories;
- Python/runtime version;
- package/dependency manifests;
- service units;
- nginx/LiteLLM configuration locations;
- database connection mechanism (without credentials);
- database schema/migration mechanism;
- runtime environment variables names (not values);
- current code version markers/build metadata;
- scheduled jobs/timers/recovery services;
- current health/model/history APIs.

Write this inventory into the work-session handoff before copying.

## 4. Capture application source without refactoring


## 5. Capture dependencies reproducibly

Do **not** copy the production venv.

Instead capture:

- existing `requirements*.txt`, `pyproject.toml`, lockfiles, or equivalent if present;
- Python version;
- `pip freeze` into a temporary comparison file;
- only convert that into a committed dependency manifest if it accurately reflects the application rather than unrelated packages.

If dependency provenance is unclear, document the gap instead of pretending the environment is reproducible.

## 6. Capture systemd and operational configuration safely

Copy relevant unit files into `ops/systemd/`.

For nginx/LiteLLM/application config:

1. inspect for embedded secrets;
2. create sanitized `.example` variants where needed;
3. replace credentials/keys/host-specific secrets with placeholders;
4. document which production-local config remains intentionally uncommitted.

Preserve behavior-significant settings such as service ordering, recovery timers, bind addresses, route generation logic, and startup commands where safe.

## 7. Capture database schema, not production data

Inventory current PostgreSQL schema/tables used by LLM Manager.

Capture either:

- existing migration files from deployed source, or
- a **schema-only** sanitized dump if no migration source exists.

Do not commit row data from tables such as settings, tokens, API keys, audit events, model history, or provider credentials.

Document that recent versions include deployment/history/benchmark structures and identify any schema that was added directly in production without a formal migration.

## 8. Verify documentation against captured code

Compare the populated framework docs against reality.

Specifically verify:

- exact service/component names;
- current management API paths;
- database table names;
- history/benchmark behavior;
- recovery desired-state behavior;
- current authentication/authorization implementation;
- LiteLLM/routing flow;
- whether `Load Configuration` and `Restore & Serve` are actually implemented or only intended;
- which parts of `docs/IMPLEMENTATION_STATUS.md` need correction.

If documentation and code disagree, **update the implementation-status/operations docs**, not the human-approved architecture direction or requirements unless the requirement itself was wrong.

Do not silently downgrade approved requirements to match current implementation.

At minimum:

2. Import/startup test in a non-production environment if feasible.
